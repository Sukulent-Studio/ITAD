# Отчёт о качестве: Green Taxi

## 1. Контекст

Вопрос из `Project Brief`: Как различается спрос на аренду велосипедов по сезонам и часам суток?

Уточняющие вопросы: как различается среднее число аренд по сезонам (зима, весна, лето, осень); как распределяется спрос по часам внутри каждого сезона и существует ли связь между сезоном и временем суток.

Смысл одной строки: один час работы системы велопроката Сеула в конкретный день — дата, час, число арендованных велосипедов, погодные условия, сезон и признак рабочего дня системы.

Гранулярность: одна строка — один час работы системы (дата + час).

Бизнес-ключ / ключ дедупликации: `(Date, Hour)`. В исходном файле 8 760 строк, что равно 365 × 24, поэтому ключ уникален.  
Ограничение: ключ уникален только на уровне системы за данный период и не различает станции, отдельные поездки или велосипеды.

Входной файл:

```text
s3://raw/seoul_bike/ingested_on=2026-10-02/SeoulBikeData.csv
```

Логическая дата загрузки — `2026-10-02`, аналитический период — `2017-12-01` – `2018-11-30` (по полю `Date`).  
Справочник зон в проверках ЛР № 3 не используется.

## 2. Профиль

В исходном CSV-файле 8 760 строк и 14 полей. При чтении S3-пути DuckDB автоматически добавляет
техническое поле `ingested_on` типа `DATE` из имени каталога, поэтому ноутбук показывает 15 полей.
Для задачи выбраны пять полей. Для каждого проверены все 8 760 строк:

| Поле                | Тип       | Примеры значений            | Проверено | Пропусков | Доля    |
|---------------------|-----------|-----------------------------|----------:|----------:|--------:|
| `Date`              | `DATE`    | `2017-12-01`, `2017-12-02`  |     8 760 |         0 | 0,000 % |
| `Hour`              | `BIGINT`  | `0`, `1`                    |     8 760 |         0 | 0,000 % |
| `Seasons`           | `VARCHAR` | `Autumn`, `Spring`          |     8 760 |         0 | 0,000 % |
| `Rented Bike Count` | `BIGINT`  | `0`, `2`                    |     8 760 |         0 | 0,000 % |
| `Functioning Day`   | `BOOLEAN` | `False`, `True`             |     8 760 |         0 | 0,000 % |

Пропуск в поле `Date` или `Hour` означал бы невозможность отнести запись к конкретному часу и построить сезонный или суточный срез; пропуск в `Rented Bike Count` — потерю основной метрики спроса; пропуск в `Seasons` — невозможность сезонного сравнения; пропуск в `Functioning Day` — невозможность отделить нерабочие часы от реального спроса. В этом снимке пропусков нет ни в одном из выбранных полей.

Полных дубликатов — 0: количество избыточных строк считается как `count(*)` минус количество строк после `SELECT DISTINCT` по всем исходным полям.  
Повторов по бизнес-ключу `(Date, Hour)` — 0: считается как сумма `count(*) - 1` по группам с `count(*) > 1`. Это подтверждает, что 8 760 строк = 365 × 24 и ключ `(Date, Hour)` уникален.

Фактический период: `2017-12-01` – `2018-11-30` (один полный год).

Распределение по часу суток в raw — равномерное, каждый час представлен одинаковым числом записей, так как каждая пара `(Date, Hour)` образует отдельную строку. Для отчёта приведены крайние часы:

| Час  | Записей |
|------|--------:|
| 0    | 365     |
| 1    | 365     |
| …    | …       |
| 23   | 365     |
| **Итого** | **8 760** |

Распределение по сезону (важно для основного вопроса проекта):

| Сезон  | Записей |
|--------|--------:|
| Autumn | 2 184   |
| Spring | 2 208   |
| Summer | 2 208   |
| Winter | 2 160   |

Значимые наблюдения:

- **Равномерное покрытие часов и сезонов.** Каждый час и каждый сезон представлены полным набором записей, поэтому сезонные и суточные средние будут сопоставимы без дополнительной нормализации. Это важно, потому что сравнение «сезон × час» в Project Brief опирается на одинаковую длину рядов.
- **Поле `Functioning Day` при чтении распознаётся как `BOOLEAN` со значениями `False` и `True`.** Логически `False` соответствует исходному `No`, а `True` — `Yes`. В нерабочие часы (`Functioning Day = False`) число аренд равно нулю, поэтому такие нули отражают недоступность сервиса, а не отсутствие спроса; при расчёте среднего спроса их нужно либо исключать, либо учитывать отдельно. Формальная проверка согласованности выполняется в шаге 3.

## 3. Правила и результаты

Условия, проверяемые строки, критичность, действия и связь с задачей описаны в разделе «Шаг 3»
[ноутбука](../notebooks/profile_quality.ipynb#rules), рядом с конкретными SQL-запросами.
Пороги заданы переменными в соответствующих ячейках.

| Правило                               | Проверено  | Нарушений  |   Доля  | Порог       | Сравнение    | Действие      |
|---------------------------------------|-----------:|-----------:|--------:|-------------|--------------|---------------|
| `pickup_and_dropoff_present`          |     48 326 |          0 |     0 % | `count ≤ 0` | Не превышен. | `quarantine`  |
| `positive_trip_duration`              |     48 326 |         48 | 0,099 % | `count ≤ 0` | Превышен.    | `quarantine`  |
| `pickup_in_january_2025`              |     48 326 |         43 | 0,089 % | `count ≤ 0` | Превышен.    | `quarantine`  |
| `negative_total_amount_is_correction` |     48 326 |        153 | 0,317 % | `count ≤ 0` | Превышен.    | `flag`        |
| `no_exact_duplicate_rows`             |     48 326 |          0 |     0 % | `count ≤ 0` | Не превышен. | `report_only` |

Длительность проверяется среди строк с обеими временными метками, период - с заполненным временем посадки,
сумма - с заполненным `total_amount`.  
В этом снимке все популяции равны 48 326 строкам.  
Нулевой порог означает, что любое нарушение требует внимания;
действие применяется к записи независимо от общего превышения порога.

Неположительная длительность и выход за период требуют карантина: иначе искажаются длительность и временные
сравнения. Отрицательная сумма может быть корректировкой; она сохраняется с флагом, а при расчёте средней
стоимости исключается. Одну из 153 таких строк исключает правило периода,
поэтому в staging остаются 152 предупреждения.

## 4. Подготовленные данные

Выходные пути на S3:

```text
s3://staging/green_tripdata/source_ingested_on=2026-09-30/staging.parquet
s3://staging/green_tripdata/source_ingested_on=2026-09-30/quarantine.parquet
```

В staging добавлен признак
`quality_negative_total_amount_is_correction_violated`: `true` - отрицательная сумма, `false` - отсутствие
этого нарушения. Это просто флаг, а не утверждение о доказанной корректировке.

Техническое поле `ingested_on` также сохраняется в обоих результатах. В файле staging 23 поля,
в файле карантина - 24.

Карантин сохраняет исходные поля, `quality_rule_ids` со списком критических причин через `;` и читаемый
`quarantine_reason`. При нескольких причинах запись сохраняется один раз.

Баланс строк: **48 326 = 48 235 + 91**. Нарушения длительности (48) и периода (43) не пересекаются.
После чтения записанных результатов критических нарушений в staging - 0; все 152 отрицательные суммы
помечены правильно, у остальных строк признак равен `false`. Бизнес-агрегаций нет, raw не изменяется.
