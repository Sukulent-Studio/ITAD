# Отчёт о качестве: Seoul Bike Sharing Demand

## 1. Контекст

**Аналитический вопрос из Project Brief.** Как различается спрос на аренду велосипедов по сезонам и часам суток? Уточняющие вопросы: как различается среднее число аренд по сезонам (зима, весна, лето, осень) и как распределяется спрос по часам внутри каждого сезона.

**Входной S3-путь.**

```text
s3://raw/seoul_bike/ingested_on=2026-10-15/SeoulBikeData.csv
```

Логическая дата загрузки — `2026-10-15`; аналитический период — `2017-12-01` – `2018-11-30` (по полю `Date`, один полный год).

**Смысл одной строки.** Один час работы системы велопроката Сеула в конкретный день: дата, час, число арендованных велосипедов, погодные условия, сезон и признак рабочего дня системы.

**Бизнес-ключ и ограничение.** Ключ — `(Date, Hour)`. В исходном файле 8 760 строк, что равно 365 × 24, поэтому ключ уникален. Ограничение: ключ описывает систему в целом за данный период и не различает станции, отдельные поездки или велосипеды. Другие наборы с той же парой `(Date, Hour)` для другого города или системы этим ключом не покрываются.

## 2. Профиль

Профиль рассчитан на сырых данных до любых преобразований. В исходном CSV 14 полей. При чтении S3-пути DuckDB автоматически добавляет поле `ingested_on` из имени каталога, поэтому при чтении видно 15 полей. Выбраны пять полей, необходимых для метрик и срезов из Project Brief.

| Поле                | Тип       | Примеры значений            | Проверено | Пропусков | Доля    |
|---------------------|-----------|-----------------------------|----------:|----------:|--------:|
| `Date`              | `DATE`    | `2017-12-01`, `2017-12-02`  |     8 760 |         0 | 0,000 % |
| `Hour`              | `BIGINT`  | `0`, `1`                    |     8 760 |         0 | 0,000 % |
| `Seasons`           | `VARCHAR` | `Autumn`, `Spring`          |     8 760 |         0 | 0,000 % |
| `Rented Bike Count` | `BIGINT`  | `0`, `2`                    |     8 760 |         0 | 0,000 % |
| `Functioning Day`   | `BOOLEAN` | `False`, `True`             |     8 760 |         0 | 0,000 % |

Полных дубликатов — 0 (`count(*)` минус `count(DISTINCT *)` по всем исходным полям). Повторов по бизнес-ключу `(Date, Hour)` — 0 (сумма `count(*) - 1` по группам с `count(*) > 1`). Фактический период: `2017-12-01` – `2018-11-30`.

Распределение по сезону (важно для основного вопроса):

| Сезон  | Записей |
|--------|--------:|
| Autumn | 2 184   |
| Spring | 2 208   |
| Summer | 2 208   |
| Winter | 2 160   |

Каждый час представлен ровно 365 записями.

**Значимые наблюдения.**

1. **Равномерное покрытие часов и сезонов.** Каждый час и каждый сезон представлены полным набором записей, поэтому сезонные и суточные средние сопоставимы без дополнительной нормализации. Это важно, потому что сравнение «сезон × час» в Project Brief опирается на одинаковую длину рядов.
2. **`Functioning Day` при чтении распознаётся как `BOOLEAN` со значениями `False` и `True`.** Логически `False` соответствует исходному `No`, а `True` — `Yes`. В нерабочие часы число аренд равно нулю, поэтому такие нули отражают недоступность сервиса, а не отсутствие спроса. При расчёте среднего спроса их нужно либо исключать, либо учитывать отдельно.

Нарушений в профиле нет: пропуски, дубликаты по ключу и полные дубликаты отсутствуют. Поэтому в разделе 3 приведена таблица правил, все результаты которой подтверждают это.

## 4. Подготовленные данные

Выходные пути на S3:

```text
s3://staging/seoul_bike/source_ingested_on=2026-10-15/staging.parquet
s3://staging/seoul_bike/source_ingested_on=2026-10-15/quarantine.parquet
```

Логическая дата `2026-10-15` совпадает с `ingested_on` исходного raw-объекта и выведена из `raw_path`, а не из даты запуска.

**Преобразования и добавленные признаки.** Аналитические имена и типы уже подходят для дальнейшего анализа: `Date` — `DATE`, `Hour` и `Rented Bike Count` — целочисленные, `Seasons` — `VARCHAR`, `Functioning Day` — `BOOLEAN`. Приведения типов и переименований не делалось. В staging добавлен признак `quality_functioning_day_consistency_violated`: `true` — час отмечен как нерабочий (`Functioning Day = false`), но `Rented Bike Count > 0`; `false` — нарушение не обнаружено. Это просто флаг, а не подтверждённая ошибка. Техническое поле `ingested_on` сохранено в обоих результатах. В файле staging 16 полей (14 исходных + `ingested_on` + признак), в файле карантина 17 полей (14 исходных + `ingested_on` + `quality_rule_ids` + `quarantine_reason`).

Карантин сохраняет исходные поля исключённых записей и содержит `quality_rule_ids` — идентификаторы критических правил через `;` — и `quarantine_reason` — читаемое объяснение причины. Каждая исключённая запись сохраняется один раз; при нескольких критических причинах сохраняются все. Карантин имеет приоритет перед флагом: если запись нарушает и критическое правило, и правило с действием `flag`, она исключается в карантин, а признак в staging не выставляется. Бизнес-агрегаций и «исправлений по догадке» нет, raw не изменяется.

**Баланс строк.** **8 760 = 8 760 + 0**. В этом снимке карантин пуст: все пять критических правил пройдены. Файл `quarantine.parquet` создаётся при каждом запуске, даже при нуле строк. После чтения записанных файлов из S3 критические нарушения в staging отсутствуют (0), дубликаты бизнес-ключа отсутствуют (0), у всех 8 760 строк признак `quality_functioning_day_consistency_violated` равен `false`.
